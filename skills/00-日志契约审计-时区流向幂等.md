# 00-日志契约审计-时区流向幂等

## 何时用
- 现象："时间列与 sample.log 不一致，UTC 下正常"；CI 在 `Asia/Shanghai` 红、UTC 绿。
- 现象：下游按行入库报脏行；stdout 里出现表头 `ts level msg` 或 `[app] first=...` 诊断行。
- 现象：`node app.js` 一跑就非 0，报错文案与代码实情对不上（如无网络调用却报 endpoint unreachable）。
- 现象：数据源为空数组时程序崩溃、被当成失败。

## 三步查法（`logcontract.sh` 一次跑完）
1. **时区一致性**：同一命令在 `UTC` / `Asia/Shanghai(+8)` / `Asia/Kolkata(+5:30)` 各起新进程，比较 stdout 的 sha256。三个不同 = 用了本地时间取值。选 `+5:30` 而非 `+8` 是因为半时区能抓"只减整 8 小时"的伪修法。
2. **流向纯净度**：`总行数 == 符合格式的行数`。不等就打印越界行，直接暴露表头与诊断串。数据行 → stdout；诊断/错误 → stderr（统一走 logger，避免两处各写一半）。
3. **退出码语义**：成功 0、失败非 0。配置态（token 未配/占位符）与空输入都不是失败；`sorted[0]` 这类直取要先判空。

## 修法（最小改动）
- 时间：`getFullYear/getMonth/getDate/getHours/getMinutes/getSeconds` → `getUTC*` 全套；格式串与函数签名/导出名不动，避免破坏只用 `formatTimestamp` 的验收。
- 流向：`console.log` → `console.error` 于 logger 的 `log()`；删表头输出；提示串改成真实原因。
- 幂等（若还要产物化）：参数写死、`-map_metadata -1 -fflags +bitexact -flags +bitexact`、manifest 不放时间戳主机名；暂存 `*.tmp` + 校验通过再 `mv` 发布，`trap ... EXIT` 清残留。

## 实测（Termux / node v26）
- 修前：SH `11:04:05` / IN `08:34:05` / UTC `03:04:05`；修后三时区 sha 相同、rc=0。
- 解除守卫后输出 8 行、合规 3 行 → 5 行污染（1 表头 + 4 诊断），已全部迁 stderr。
- `records=[]` 修前 `TypeError` at `sorted[0].ts`，修后 rc=0 且 stdout 0 字节。

## 坑
- `cp 备份 && 打补丁`：在 Termux `/tmp` 不可写时 cp 失败、`&&` 短路，脚本"看起来成功"其实没改；落盘后必须回读 `git diff`。
- 幂等比对用 `sha256sum out/*` 会被非目标文件带偏（另一次探针把某个文件跑空了），要**两次真实运行**逐文件比。
- 只跑 `UTC` 就算验收通过，是最常见的假绿。
